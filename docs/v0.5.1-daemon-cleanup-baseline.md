# v0.5.1 — baseline of the daemon state cleanup fix (issue #8)

Taken **2026-08-01** on master `958af34` (tag `v0.5.1`, merge of the hotfix
`hotfix/daemon-successor-state`) on the production vault. Windows 11 Pro 26200,
Python 3.10.

This is **a baseline of a fix**, not of a release: it records not the state of the
system but **the contract of one function** — `SearchDaemon._cleanup_state()` — in
every state in which a dying daemon can find its state files. The slice of corpus
state at the release lives separately, in
[v0.5.0-baseline.md](v0.5.0-baseline.md); it is deliberately absent here.

The machine-readable slice sits alongside:
**`docs/v0.5.1-daemon-cleanup-baseline.json`**.

---

## 1. What was fixed

The daemon polls its shutdown flag **between** requests, so a busy daemon
survives its own SIGTERM for exactly as long as the current request lasts — and
since 0.4.0, in-daemon indexing (`{"cmd":"index"}`) made multi-minute requests
normal. `stop_daemon()` returns about 0.5 s after the signal, the starter brings
up a replacement, the replacement binds the port and writes **its own**
`daemon.json` / `daemon.port` / `daemon.pid` — and only then does the old daemon
reach its `finally` and delete all three unconditionally, erasing the successor's
identity.

```
t0  stop_daemon(): SIGTERM to the old daemon (busy in _serve_conn), state cleaned
t1  start_daemon(): a new daemon is spawned
t2  the new daemon binds the port, writes daemon.json (pid=NEW)
t3  the old daemon finishes its request and leaves the loop
t4  the old daemon in finally: unlink daemon.json/port/pid   <-- the successor's!
t5  the starter pings nowhere for 30 s -> "FAILED to start"
    (the new daemon is alive but unreachable for every client)
```

The symptom is doubly deceptive: `mb daemon start` reports a failed start about a
daemon that **came up successfully** and is visible in `ps`, and after that every
`ping`/`search` fails until the orphan is killed by hand.

Where the fix lives: `singularity/search/daemon.py:168` (the call from `finally`)
and `singularity/search/daemon.py:173` (`_cleanup_state` itself).

Source: GitHub issue #8, @esevinale, reproduced twice on macOS. The bug was
present in every version since the daemon's identity state appeared (AUD-11).

## 2. Reproduction

```bash
PYTHONIOENCODING=utf-8 python tools/daemon_cleanup_baseline.py \
    > docs/v0.5.1-daemon-cleanup-baseline.json

```

`PYTHONIOENCODING` is mandatory on Windows: a bare redirect encodes stdout in the
console code page and mangles everything non-ASCII in the snapshot.

The script refuses to take a baseline if `import singularity` resolved to a
checkout other than the one it was started from (an editable install pulls the
package from where it was installed, not from the cwd) — a baseline taken against
somebody else's tree is worse than no baseline. To check by hand: the
`environment.package_path` field in the JSON must point into the current checkout.

## 3. The contract: whoever owns the state deletes it

Ownership is determined by **`instance_id`** (a fresh uuid4 per instance), not by
pid as the issue proposed: pids are reused, and pid reuse is exactly the class of
race this fix closes. For legacy state with no `instance_id` (pre-AUD-11), the pid
comparison is kept as a fallback.

| State of `daemon.json` | Expectation | Why |
|---|---|---|
| the successor's `instance_id`, a different pid | **keep** | the successor has already bound the port and written its identity |
| the successor's `instance_id`, **the same** pid | **keep** | the OS reused the pid — `instance_id` decides |
| this instance's `instance_id` | delete | an ordinary shutdown, the state is still ours |
| legacy with no `instance_id`, our pid | delete | the pid fallback |
| legacy with no `instance_id`, a foreign pid | **keep** | the same fallback, a different owner |
| the file is absent | delete | nobody claims ownership, and port/pid are our leftovers |
| the file is corrupt | delete | unreadable state is unclaimed state, like an absent one |

All seven rows are checked in the snapshot's `ownership_matrix`, all `pass: true`.

The signature `_cleanup_state(cfg, own_pid, own_instance_id=None)` keeps
compatibility with the call shape from the issue — `_cleanup_state(cfg, own_pid=111)`
works and is checked separately (`reporter_signature_compat`).

The check against a live daemon is not a mock: against a **running** daemon
(pid 21868, instance `5458310893f5460ebda4f24f950257dc`), `_cleanup_state()` is
called on behalf of a predecessor that has just exited. Before the fix that call
would have removed all three files and left a live but unreachable daemon. After
the fix all three are in place and the daemon answers a `ping`.

## 5. What this baseline does NOT prove

- **The Windows run does not cover the original scenario.** `proc.kill` on Windows
  terminates a process hard and `finally` does not run at all — the bug does not
  reproduce there, and `live_daemon_check` emulates the predecessor's exit by
  calling the function rather than by a real race between two processes. The real
  race (SIGTERM to a busy daemon plus the start of a replacement) is only
  checkable on POSIX.
- **The absolute values in the snapshot are unstable** by construction:
  `live_pid`, `instance_id`, `taken_at` and the test timings change from run to
  run. What is canonical is `expected`/`actual`/`pass` and the method of taking
  them.
- **`stop_daemon()` still does not wait for the process to actually exit** — it
  returns 0.5 s after the signal, so a busy daemon may hold the port for seconds
  after a "successful" `mb daemon stop`. A separate symptom, not fixed in v0.5.1,
  and not recorded here.

## 6. How to catch a regression

The sign of the bug returning in the field is `mb daemon start` reporting
`FAILED to start` after the full 30-second timeout, while `.mb/daemon.log`
contains `[daemon] listening on 127.0.0.1:<port>`, the process is alive, and
`daemon.json` is missing. The check: re-take the baseline and look at the
`successor_owns__*` rows — if they moved into `removed`, the ownership check is
broken or bypassed.
