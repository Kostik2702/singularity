# v0.5.1 — baseline фикса очистки state демона (issue #8)

Снято **2026-08-01** на master `958af34` (тег `v0.5.1`, merge хотфикса
`hotfix/daemon-successor-state`) на боевом vault. Windows 11 Pro 26200,
Python 3.10.

Это **baseline фикса**, а не релиза: он фиксирует не состояние системы, а
**контракт одной функции** — `SearchDaemon._cleanup_state()` — во всех
состояниях, в которых умирающий демон может застать свои state-файлы. Срез
состояния корпусов на релизе живёт отдельно, в
[v0.5.0-baseline.md](v0.5.0-baseline.md); здесь его нет намеренно.

Машиночитаемый срез рядом: **`docs/v0.5.1-daemon-cleanup-baseline.json`**.

---

## 1. Что чинилось

Демон опрашивает свой shutdown-флаг **между** запросами, поэтому занятый
демон переживает собственный SIGTERM ровно настолько, насколько длится
текущий запрос — а с 0.4.0 in-daemon индексация (`{"cmd":"index"}`) сделала
многоминутные запросы нормой. `stop_daemon()` возвращается примерно через
0.5 с после сигнала, стартер поднимает замену, замена биндит порт и пишет
**свои** `daemon.json` / `daemon.port` / `daemon.pid` — и только после этого
старый демон доходит до своего `finally` и сносит все три безусловно,
удаляя идентичность преемника.

```
t0  stop_daemon(): SIGTERM старому демону (занят в _serve_conn), чистка state
t1  start_daemon(): спавн нового демона
t2  новый демон биндит порт, пишет daemon.json (pid=NEW)
t3  старый демон дорабатывает запрос, выходит из цикла
t4  старый демон в finally: unlink daemon.json/port/pid   <-- преемника!
t5  стартер 30 с пингует в никуда -> "FAILED to start"
    (новый демон жив, но недостижим для всех клиентов)
```

Симптом обманчив вдвойне: `mb daemon start` рапортует провал старта про
демона, который **успешно поднялся** и виден в `ps`, а дальше падают все
`ping`/`search`, пока сироту не убьют руками.

Место фикса: `singularity/search/daemon.py:168` (вызов из `finally`) и
`singularity/search/daemon.py:173` (сама `_cleanup_state`).

Источник: GitHub issue #8, @esevinale, воспроизведено дважды на macOS.
Баг присутствовал во всех версиях с момента появления identity-состояния
демона (AUD-11).

## 2. Воспроизведение

```bash
PYTHONIOENCODING=utf-8 python tools/daemon_cleanup_baseline.py \
    > docs/v0.5.1-daemon-cleanup-baseline.json
python -m pytest tests/test_daemon_identity.py -q
```

`PYTHONIOENCODING` на Windows обязателен: голый редирект кодирует stdout в
кодовой странице консоли и корёжит в снимке всё не-ASCII.

Скрипт отказывается снимать baseline, если `import singularity` разрешился
не в тот checkout, из которого он запущен (editable-install тянет пакет
туда, откуда ставился, а не в cwd) — снятый по чужому дереву baseline хуже,
чем его отсутствие. Проверить руками: поле `environment.package_path` в
JSON должно указывать в текущий checkout.

## 3. Контракт: кто владеет state, тот и удаляет

Владение определяется по **`instance_id`** (свежий uuid4 на инстанс), а не
по pid, как предлагалось в issue: pid переиспользуем, а переиспользование
pid — ровно тот класс гонки, который этот фикс и закрывает. Для legacy-state
без `instance_id` (до AUD-11) сравнение по pid оставлено как fallback.

| Состояние `daemon.json` | Ожидание | Почему |
|---|---|---|
| `instance_id` преемника, другой pid | **сохранить** | преемник уже забиндил порт и записал идентичность |
| `instance_id` преемника, **тот же** pid | **сохранить** | ОС переиспользовала pid — решает `instance_id` |
| `instance_id` этого инстанса | удалить | обычное завершение, state всё ещё наш |
| legacy без `instance_id`, наш pid | удалить | fallback на pid |
| legacy без `instance_id`, чужой pid | **сохранить** | тот же fallback, владелец другой |
| файла нет | удалить | владельца никто не заявляет, port/pid — наши остатки |
| файл битый | удалить | нечитаемый state = незаявленный, как и отсутствующий |

Все семь строк проверяются в `ownership_matrix` снимка, все `pass: true`.

Сигнатура `_cleanup_state(cfg, own_pid, own_instance_id=None)` сохраняет
совместимость с формой вызова из issue — `_cleanup_state(cfg, own_pid=111)`
работает и проверяется отдельно (`reporter_signature_compat`).

## 5. Чего этот baseline НЕ доказывает

- **Windows-прогон не покрывает исходный сценарий.** `proc.kill` на Windows
  завершает процесс жёстко, `finally` не выполняется вовсе — баг там не
  воспроизводится, а `live_daemon_check` эмулирует выход предшественника
  вызовом функции, а не реальной гонкой двух процессов. Настоящая гонка
  (SIGTERM занятому демону + старт замены) проверяема только на POSIX.
- **Абсолютные значения в снимке нестабильны** по построению: `live_pid`,
  `instance_id`, `taken_at`, тайминги тестов меняются от прогона к прогону.
  Эталонными являются `expected`/`actual`/`pass` и метод снятия.
- **`stop_daemon()` по-прежнему не ждёт фактического выхода процесса** —
  возвращается через 0.5 с после сигнала, поэтому занятый демон может
  держать порт секундами после «успешного» `mb daemon stop`. Отдельный
  симптом, в v0.5.1 не чинился, здесь не зафиксирован.

## 6. Как ловить регрессию

Признак возврата бага в поле — `mb daemon start` рапортует
`FAILED to start` после полного 30-секундного таймаута, при этом в
`.mb/daemon.log` есть `[daemon] listening on 127.0.0.1:<port>`, процесс жив,
а `daemon.json` отсутствует. Проверка: пересняв baseline, смотреть строки
`successor_owns__*` — если они переехали в `removed`, ownership-проверка
сломана или обойдена.
