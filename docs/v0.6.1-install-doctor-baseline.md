# v0.6.1 — baseline of the config write path (and the first POSIX snapshot)

Taken **2026-08-04** on master `b0c7901` (merge of `fix/config-set-nested-keys` +
`fix/baseline-locator-isolation`, tag `v0.6.1`) on the production vault.
macOS 26.6 arm64, Python 3.13.14.

A continuation of the v0.6.0 baseline with the same tool
(`tools/install_doctor_baseline.py`), with one new section and on a **different
OS**. Both differences matter and are discussed below.

The machine-readable slice sits alongside:
**`docs/v0.6.1-install-doctor-baseline.json`**.

---

## 1. What was fixed

One defect, found while executing v0.6.0's own output on the machine this release
was cut from.

| Symptom | The real cause |
|---|---|
| `mb config set projects.singularity.path "<posix>"` reports success — `mb doctor` repeats the same WARN | `config set` did `{**cfg.data, args.key: value}`: a dotted key became a **literal top-level key** that nobody reads |
| `mb config get <the same key>` confirms the write | `Config.get` looks for an exact match first — and finds that very junk key |
| `mb daemon reload` answers `config_changed: ["projects.singularity.path"]` | the daemon compares configs by top-level keys, and the junk key really did change |
| `mb config validate` says nothing | unknown keys are warnings, and `set` did not print them |
| `mb project add` — the sanctioned way to re-point a project — silently loses `group` and `about` | the entry was rebuilt from the flags, with no merge into the existing one |

Every key `A6-config-paths` lists (introduced in #14, v0.6.0) is nested:
`projects.<id>.path`, `llm.server_bin`, `llm.models.<name>.gguf`,
`llm.models.<name>.args[i]`. That is, **the fix the doctor printed worked for not
one of the keys the doctor prints**, and four independent checks confirmed a write
that never happened.

## 2. Reproduction

```bash
PYTHONIOENCODING=utf-8 python tools/install_doctor_baseline.py \
    > docs/v0.6.1-install-doctor-baseline.json
```

From the repository root, on a checkout **with** the fixes, with a live daemon
(otherwise the `issue_12_live_config_reload` section writes `ran: false` with a
reason).

The negative control (mandatory for a new section — a check that does not fail on
broken code is worth nothing):

```bash
git worktree add --detach <tmp> <the commit before the fix>
cp tools/install_doctor_baseline.py <tmp>/tools/
python -c "…; m.nested_config_write(Path(td))"   # from <tmp>
```

On the pre-fix tree **4 of 5** cases fail. The fifth — the read-back — passes,
confirming the junk key. That is the mechanics of the trap, recorded as a check.

## 3. What was recorded

### 3.1 The config write path — `config_write_path` (a new section)

Five cases through the **real CLI** (`bin/_launch.py mb …`) against a throwaway
vault, graded by the file on disk rather than by an exit code:

| Case | What is checked |
|---|---|
| `config set projects.p.path /posix/p` | the value landed in the nested node; there are no dotted keys at the top level; `group`/`about` are intact |
| `config set llm.models.m.args[3] …` | the indexed form (`args[i]`) — exactly the one `A6` prints |
| `config set projects.ghost.path /x` | exit 1, `no such config section`, the file did not change by a byte |
| `config get projects.p.path` | the read-back answers in the same notation |
| `project add p /posix/p2` | re-pointing preserves `group` and `about` |

All five `pass: true`.

**Why this section did not exist before.** v0.6.0 recorded the live cycle
`set → read-back → reload → restore` (#12) — and it was honest, but it wrote
**straight through `cfg.data`** and only for the flat key `excerpt_chars`. It
checked whether a change reaches the daemon and never once typed the command a
user types. The defect lay exactly in the gap between those two questions.

### 3.2 Finding the CLI outside PATH — `issue_10_cli_locator`

5/5 layouts, `search_locations: 8`, and a new field
`suppressed_env: ["NVM_BIN", "NVM_DIR"]`.

The first run on this machine gave **3/5** — and that was not a regression but a
measurement showing the operator's terminal. `cli_locator` reads `$NVM_BIN` /
`$NVM_DIR` / `$FNM_MULTISHELL_PATH` **before** consulting `~`, so substituting
`Path.home()` does not redirect the nvm branch, and the synthetic layouts are
invisible from any interactive shell where nvm is sourced. v0.6.0 passed only
because it was taken from a shell without nvm. In the tests this surface has been
neutralised since #10 (`_no_real_version_managers` in `tests/conftest.py`) — now
in the tool too, with a record of what exactly was suppressed.

### 3.3 The doctor — `issue_11_13_14_15_doctor`

`exit_code: 0`, **34 PASS / 1 WARN**. The single WARN is `A6-config-paths`, and it
is correct: 8 of the 10 paths in this config are Windows paths on macOS.

### 3.4 Paths in the config — `issue_14_config_paths`

10 path keys, 8 of them `foreign_os: windows`. **The first field run rather than a
fixture**: v0.6.0 was taken on Windows, where Windows paths are native, and the
`foreign_os` branch was empty in that snapshot.

### 3.5 Launchers and the live daemon

`issue_9_16_launchers`: 8 runs (a neutral and a shadowing CWD), pass.
`issue_12_live_config_reload`: `150 → 151 → 150`,
`reload_reported_changed: ["excerpt_chars"]`, pass.

## 4. Evidence

- `all_pass: true`.
- Tests in the snapshot: **1761 passed, 25 skipped** (the tool excludes
  `tests/test_gemini_e2e.py`; a full run is 1762 passed, 25 skipped).
- 21 new tests: `tests/test_config_nested_keys.py`.

## 5. What this baseline does NOT prove

- **A coverage hole mirroring v0.6.0's.** That snapshot was on Windows, this one
  on macOS. Here the exec bit, `~/.local/bin` and `foreign_os` were finally
  checked against a real cross-OS config, but the Windows PATH registry branch,
  the `.cmd` shims and the Windows scheduler branches did not execute in this run
  at all.
- **The defect was found on one machine, not caught by the matrix.** It would have
  been invisible to the new section as well, had it not been written on purpose:
  the old baseline passed.
- **`config_write_path` works on a throwaway vault.** It does not prove that a
  production config survives a write — only that the command does what it says.
- **The absolute values are unstable** by construction (`taken_at`, timings, the
  set of WARNs, the set of path keys). What is canonical are the `pass` fields and
  the method of taking them.

## 6. How to catch a regression

- Any `pass: false` in `config_write_path` — the write path has diverged again
  from what `A6` prints. A non-empty `literal_top_level_keys` case means exactly
  this bug is back.
- `issue_10_cli_locator.suppressed_env` missing from the snapshot — the tool is
  measuring the shell it was launched from again, and its verdict on the locator
  means nothing.
- `A6-config-paths` reporting PASS while the paths are plainly foreign — either
  `path_entries` or `foreign_os` broke.
- `project add` with no `group`/`about` in the `entry` — the silent loss of
  metadata when re-pointing a project is back.
