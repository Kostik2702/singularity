# v0.6.1 — baseline пути записи конфига (и первый POSIX-снимок)

Снято **2026-08-04** на master `b0c7901` (merge `fix/config-set-nested-keys` +
`fix/baseline-locator-isolation`, тег `v0.6.1`) на боевом vault.
macOS 26.6 arm64, Python 3.13.14.

Продолжение baseline v0.6.0 тем же инструментом
(`tools/install_doctor_baseline.py`), с одной новой секцией и на **другой ОС**.
Обе разницы существенны и обсуждаются ниже.

Машиночитаемый срез рядом: **`docs/v0.6.1-install-doctor-baseline.json`**.

---

## 1. Что чинилось

Один дефект, найденный при исполнении собственного вывода v0.6.0 на машине,
с которой этот релиз и выпускался.

| Симптом | Настоящая причина |
|---|---|
| `mb config set projects.singularity.path "<posix>"` рапортует успех — `mb doctor` повторяет тот же WARN | `config set` делал `{**cfg.data, args.key: value}`: dotted-ключ становился **литеральным ключом верхнего уровня**, которого не читает никто |
| `mb config get <тот же ключ>` подтверждает запись | `Config.get` сначала ищет точное совпадение — и находит тот самый мусорный ключ |
| `mb daemon reload` отвечает `config_changed: ["projects.singularity.path"]` | демон сравнивает конфиги по ключам верхнего уровня, мусорный ключ действительно изменился |
| `mb config validate` молчит | неизвестные ключи — это warnings, а `set` их не печатал |
| `mb project add` — штатный способ перенацелить проект — молча теряет `group` и `about` | запись собиралась заново из флагов, без слияния с существующей |

Все ключи, которые перечисляет `A6-config-paths` (введён в #14, v0.6.0),
вложенные: `projects.<id>.path`, `llm.server_bin`, `llm.models.<name>.gguf`,
`llm.models.<name>.args[i]`. То есть **напечатанный доктором фикс не работал
ни для одного ключа, который доктор печатает**, и четыре независимые проверки
подтверждали несостоявшуюся запись.

## 2. Воспроизведение

```bash
PYTHONIOENCODING=utf-8 python tools/install_doctor_baseline.py \
    > docs/v0.6.1-install-doctor-baseline.json
```

Из корня репозитория, на чекауте **с** фиксами, при живом демоне (иначе
секция `issue_12_live_config_reload` пишет `ran: false` с причиной).

Негативный контроль (обязателен для новой секции — проверка, которая не падает
на сломанном коде, ничего не стоит):

```bash
git worktree add --detach <tmp> <коммит до фикса>
cp tools/install_doctor_baseline.py <tmp>/tools/
python -c "…; m.nested_config_write(Path(td))"   # из <tmp>
```

На дофиксовом дереве падают **4 из 5** кейсов. Пятый — read-back — проходит,
подтверждая мусорный ключ. Это и есть механика ловушки, зафиксированная в
виде проверки.

## 3. Что зафиксировано

### 3.1 Путь записи конфига — `config_write_path` (новая секция)

Пять кейсов через **настоящий CLI** (`bin/_launch.py mb …`) против одноразового
vault, оценка — по файлу на диске, а не по коду возврата:

| Кейс | Что проверяется |
|---|---|
| `config set projects.p.path /posix/p` | значение легло во вложенный узел; ключей с точкой на верхнем уровне нет; `group`/`about` целы |
| `config set llm.models.m.args[3] …` | индексная форма (`args[i]`) — ровно та, что печатает `A6` |
| `config set projects.ghost.path /x` | exit 1, `no such config section`, файл не изменился ни на байт |
| `config get projects.p.path` | read-back отвечает в той же нотации |
| `project add p /posix/p2` | перенацеливание сохраняет `group` и `about` |

Все пять `pass: true`.

**Почему этой секции не было раньше.** v0.6.0 фиксировал живой цикл
`set → read-back → reload → restore` (#12) — и он был честен, но писал
**через `cfg.data` напрямую** и только по плоскому ключу `excerpt_chars`.
Он проверял, доходит ли изменение до демона, и ни разу не набрал команду,
которую набирает пользователь. Дефект был ровно в промежутке между этими
двумя вопросами.

### 3.2 Поиск CLI мимо PATH — `issue_10_cli_locator`

5/5 раскладок, `search_locations: 8`, новое поле
`suppressed_env: ["NVM_BIN", "NVM_DIR"]`.

Первый прогон на этой машине дал **3/5** — и это была не регрессия, а
измерение, показывающее терминал оператора. `cli_locator` читает `$NVM_BIN` /
`$NVM_DIR` / `$FNM_MULTISHELL_PATH` **до** обращения к `~`, поэтому подмена
`Path.home()` не перенаправляет nvm-ветку, и синтетические раскладки
невидимы из любой интерактивной оболочки, где nvm засорсен. v0.6.0 прошёл
только потому, что снимался из оболочки без nvm. В тестах эта поверхность
нейтрализована с #10 (`_no_real_version_managers` в `tests/conftest.py`) —
теперь и в инструменте, с записью того, что именно было подавлено.

### 3.3 Доктор — `issue_11_13_14_15_doctor`

`exit_code: 0`, **34 PASS / 1 WARN**. Единственный WARN — `A6-config-paths`,
и он верен: 8 путей из 10 в этом конфиге — Windows-пути на macOS.

### 3.4 Пути в конфиге — `issue_14_config_paths`

10 путевых ключей, 8 `foreign_os: windows`. **Впервые полевой прогон, а не
фикстура**: v0.6.0 снимался на Windows, где Windows-пути родные, и ветка
`foreign_os` в том снимке была пуста.

### 3.5 Лаунчеры и живой демон

`issue_9_16_launchers`: 8 прогонов (нейтральный и затеняющий CWD), pass.
`issue_12_live_config_reload`: `150 → 151 → 150`, `reload_reported_changed:
["excerpt_chars"]`, pass.

## 5. Чего этот baseline НЕ доказывает

- **Зеркальная к v0.6.0 дыра в покрытии.** Тот снимок был на Windows, этот —
  на macOS. Здесь наконец проверены exec-бит, `~/.local/bin` и `foreign_os`
  на настоящем кросс-ОС конфиге, но ветка реестра Windows PATH, `.cmd`-шимы и
  Windows-ветки планировщика в этом прогоне не исполнялись вовсе.
- **Дефект найден на одной машине, а не отловлен матрицей.** Он был бы
  невидим и для новой секции, если бы её не написали специально: старый
  baseline проходил.
- **`config_write_path` работает на одноразовом vault.** Он не доказывает,
  что боевой конфиг переживёт запись, — только что команда делает то, что
  говорит.
- **Абсолютные значения нестабильны** по построению (`taken_at`, тайминги,
  состав WARN, набор путевых ключей). Эталонны `pass`-поля и метод снятия.

## 6. Как ловить регрессию

- Любой `pass: false` в `config_write_path` — путь записи снова разошёлся с
  тем, что печатает `A6`. Кейс `literal_top_level_keys` непустой — вернулся
  ровно этот баг.
- `issue_10_cli_locator.suppressed_env` отсутствует в снимке — инструмент
  снова измеряет оболочку, из которой его запустили, и его вердикт по
  локатору ничего не значит.
- `A6-config-paths` со статусом PASS при заведомо чужих путях — сломалась
  либо `path_entries`, либо `foreign_os`.
- `project add` без `group`/`about` в `entry` — вернулась молчаливая потеря
  метаданных при перенацеливании проекта.
