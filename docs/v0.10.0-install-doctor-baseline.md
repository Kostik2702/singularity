## 2. Почему это безопасно — и как снимок это проверяет

Фасад — тот класс изменений, который выглядит хорошо в демонстрации и гниёт в
щелях: групповой путь тихо расходится с прямым, help перечисляет команду,
которую парсер потерял, код возврата меняется без чьего-либо решения. Поэтому
новая секция `v0100_cli_window` спрашивает ровно это, и главные строки в ней —
**побайтовые**, а не «делает то же самое»:

| Проверка | Результат |
|---|---|
| витрина перечисляет ровно то, что объявляет `facade.WINDOW` | OK |
| `mb help --all` называет **все** команды парсера | OK |
| `mb service daemon --help` == `mb daemon --help` (stdout байт в байт) | OK |
| `mb setup config --help` == `mb config --help` | OK |
| `mb curator nightly --help` == `mb nightly --help` | OK |
| `mb status stats --help` == `mb stats --help` | OK |
| хост по-прежнему диспатчится в свою команду (`mb curator` не стал листингом) | OK |
| коды возврата: `mb help` → 0, `mb <неизвестное>` → 2, `mb service <неизвестное>` → 2 | OK |

Последняя строка закрепляет **единственное изменение поведения** этого релиза,
чтобы поздняя правка не сдвинула его молча: `docs/UPGRADE.md` обещает ровно эти
три числа.

## 4. Что снимок НЕ проверяет

- **Витрину на Windows.** Проверены логика и коды возврата на macOS; предыдущие
  четыре снимка покрывали Windows, но там ещё не было секции `v0100_cli_window`.
  Первый же снимок на Windows-машине после обновления закроет и это.
- **Что группы удобны.** Побайтовое равенство доказывает, что путь ведёт в ту же
  команду, и ничего не говорит о том, найдёт ли человек нужное. Единственный
  измеритель этого — `mb reflect`, и он теперь хотя бы имеет читателя
  (секция «Здоровье по данным» в скилле `memory-curator`).
- **Скиллы на групповых путях.** Их там нет по решению владельца: автоматизация
  остаётся на прямых путях, поэтому снимок и не пытается их грейдить.
