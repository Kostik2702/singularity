# v0.6.0 — baseline of installation and doctor honesty (issues #9–#16)

Taken **2026-08-04** on master `d592f72` (merge of `fix/install-doctor-batch`,
tag `v0.6.0`) on the production vault. Windows 11 Pro 26200, Python 3.10.

This is **a release baseline**, but not one of the corpora: it records not "how
much of what is indexed" but **what the system says about itself** — what
`mb doctor` reports, whether the launchers survive a shadowing CWD, whether a CLI
hidden by a version manager is found, which paths in the config are enumerated at
all, and whether a live daemon picks up a config change. Exactly the questions the
reporter had to answer by hand.

The machine-readable slice sits alongside:
**`docs/v0.6.0-install-doctor-baseline.json`**.

---

## 1. What was fixed

Eight issues from one clean install of v0.5.1 on macOS. They all share one shape:
**the installer exited 0, every diagnostic was green — and the feature silently
did not work.**

| # | Symptom | The real cause |
|---|---|---|
| 9 | `./install/install.sh` → `permission denied`, exit 126 | mode `100644` in the git index, not `100755` |
| 15 | after a successful install, `mb` → `command not found` | console scripts are generated into `<engine>/.venv/bin`, which nobody puts on `PATH`; the shims in `bin/` are `100644` too |
| 16 | `sh singularity/bin/mb` from `~/projects` → `ImportError … (unknown location)` | `-m` puts the CWD first on `sys.path`, the neighbouring `singularity/` directory becomes a namespace package and shadows the installed one |
| 10 | Gemini hooks silently skipped with `@google/gemini-cli@0.53.1` installed | presence was detected by directory, the version through `shutil.which`; nvm is a shell function, invisible to a non-interactive process |
| 11 | the first commit into the vault fails with `Author identity unknown` | `D4-cli` checked for the presence of the `git` binary, not for the ability to commit |
| 12 | `mb index rebuild --code` reports `files: 0` forever | the daemon serves a `Config` captured at start-up; `reload` reloaded the **indexes**, not the config |
| 13 | `[PASS] K1-code-index: 0 chunk(s) from 0 file(s)` | "built, but from zero files" fell through into the success branch |
| 14 | after the vault moved between operating systems, 9 paths are dead and the doctor says nothing about 8 of them | exactly one key was validated (`code_repos_dir`) |

Number 16 deserves a note of its own: the report was about `bin/`, but `-m` is a
mechanism, and it was still alive in three more places the report did not cover,
all of which inherit somebody else's working directory: the spawn of the detached
daemon and the scheduler jobs in all four backends. On the Linux layout from our
own README (`git clone <url> ~/singularity` → `$HOME` contains `singularity/`),
every nightly rebuild and every login watcher died silently.

## 2. Reproduction

```bash
PYTHONIOENCODING=utf-8 python tools/install_doctor_baseline.py \
    > docs/v0.6.0-install-doctor-baseline.json
python -m pytest tests/ -q
```

`PYTHONIOENCODING` is mandatory on Windows: a bare redirect encodes stdout in the
console code page and mangles everything non-ASCII in the snapshot. In PowerShell
`>` additionally writes a UTF-8 BOM, which `json.load` will not accept — take it
through `$out = & python …` and
`[IO.File]::WriteAllText(..., UTF8Encoding $false)`.

The script refuses to take a baseline if `import singularity` resolved to a
checkout other than the one it was started from — inherited from the v0.5.1
baseline for the same reason: a baseline taken against somebody else's tree is
worse than no baseline.

## 3. What was recorded

### 3.1 Launchers (#9, #15, #16) — `issue_9_16_launchers`

Every launcher is run from **two** directories the script creates itself: a
neutral one and one containing `singularity/`. The second is exactly the parent of
a standard clone.

| Launcher | neutral CWD | shadowing CWD |
|---|---|---|
| `bin/_launch.py mb` | pass | **pass** |
| `bin/_launch.py imgqa` | pass | **pass** |
| `bin/_launch.py design-scout` | pass | **pass** |
| `sh bin/mb` | pass | **pass** |

Plus the modes in the git index — the index specifically, not the working copy: on
Windows the working-copy mode means nothing, while a POSIX clone gets exactly the
indexed one.

```
install/install.sh 100755 · bin/mb 100755 · bin/imgqa 100755 · bin/design-scout 100755
```

The sign of the bug returning in a snapshot is the field `namespace_shadowed: true`
in any row (the namespace-package signature `unknown location` appeared in
stderr).

### 3.2 Finding the CLI outside PATH (#10) — `issue_10_cli_locator`

The version-manager layouts are synthetic: a real nvm cannot be assumed on an
arbitrary machine, and what is checked here is the **search order**, not this
machine.

| Layout | Found |
|---|---|
| `~/.nvm/versions/node/v24.19.0/bin` | yes |
| `~/.nvm/versions/node/v18.20.0/bin` | yes |
| `~/.volta/bin` | yes |
| `~/.local/share/fnm/.../installation/bin` | yes |
| three Node versions at once | `v24.19.0` chosen |

The last row is not about "found" but about **numeric** ordering: lexicographically
`v9` is greater than `v10`, and "the newest" would have become the oldest.

### 3.3 The doctor (#11, #13, #14, #15) — `issue_11_13_14_15_doctor`

**`PASS 33 | WARN 2`**, and both WARNs are real findings the old doctor never
showed:

- `A6-config-paths`: three `gguf` files from `llm.models.*` are physically absent
  on this machine;
- `D7-cli-on-path`: `mb` resolves to `…\Python310\Scripts\mb.exe` rather than to
  this engine's venv — that is, **a different** Singularity installation is
  answering for the vault.

New checks in this release: `A6-config-paths`, `D7-cli-on-path`,
`D8-git-identity`. In the snapshot they are listed in a separate field,
`new_in_this_release`.

### 3.4 Paths in the config (#14) — `issue_14_config_paths`

**10** path entries of the production config are enumerated, including
`llm.models.qwythos9b.args[14]` — exactly the nested case
(`--chat-template-file` inside an argument list) the report named separately. The
snapshot carries only the **keys**: the values are this machine's business.

Two different states are distinguished: `foreign_os` (the value belongs to another
OS — that is not "lost", that is "from another machine") and plain `missing`.

### 3.5 The live daemon and the config (#12) — `issue_12_live_config_reload`

Not a mock: a harmless key is changed against a **running** daemon, and then
everything is put back.

```
daemon before the write             excerpt_chars = 150
write into the config               excerpt_chars = 151
daemon after the write, pre-reload  excerpt_chars = 150   <-- exactly bug #12
mb daemon reload                    config_changed: ["excerpt_chars"]
daemon after the reload             excerpt_chars = 151
restored                            excerpt_chars = 150
```

Before the fix the third line looked the same, and the fifth was `150` too, with
nothing reporting it.

`1753` against `1754` in an ordinary run is exactly the one test

## 5. What this baseline does NOT prove

- **Not one of the eight bugs was reproduced on the original OS.** Every report
  came from macOS 15 / zsh; the snapshot was made on Windows 11. What is checked
  here is the behaviour **after** the fix, and some of the mechanics on Windows
  are fundamentally different: the exec bit has no effect, `~/.local/bin` is not
  used (on Windows it is a registry branch), and the `sudo`/nvm layouts simply do
  not exist. The POSIX half of `install/register_path.py` is covered by tests
  only.
- **`A6-config-paths` was not checked against a real cross-OS config.** On this
  machine Windows paths are native, so the `foreign_os` branch is empty in the
  snapshot; it is covered by tests on a fixture from the report, but not by a
  field run.
- **`D7-cli-on-path` recorded a WARN, not a PASS.** On this machine `mb` really
  does belong to another installation. That row of the snapshot describes the real
  state of the machine, not a reference for "how it should be after an install".
- **The absolute values are unstable** by construction: `taken_at`, the timings,
  the chunk count and the set of WARNs depend on the machine. What is canonical
  are the `pass` fields and the method of taking them.
- **The gate "install → PATH → mb works" was not run from scratch.** A full clean
  install on a fresh machine was not reproduced here; phase 4e is covered by unit
  tests and its own `mb doctor` check, not by an end-to-end installer run.

## 6. How to catch a regression

- `namespace_shadowed: true` in `issue_9_16_launchers.runs` — `-m` is back
  somewhere in the launch chain (or a shim starts the package again instead of the
  file).
- Any mode ≠ `100755` in `executable_bit_in_index` — the exec bit was lost again;
  `tests/test_repo_file_modes.py` catches this too.
- `issue_12_live_config_reload.daemon_value_after_reload` ≠ the written value —
  `reload` has stopped re-reading the config again.
- `K1-code-index` with status `PASS` and `0 file(s)` in the text — #13 is back, and
  with it went the check that catches #12 first.
