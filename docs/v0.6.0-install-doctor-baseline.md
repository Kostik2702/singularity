# v0.6.0 — baseline честности установки и доктора (issues #9–#16)

Снято **2026-08-04** на master `d592f72` (merge `fix/install-doctor-batch`,
тег `v0.6.0`) на боевом vault. Windows 11 Pro 26200, Python 3.10.

Это **baseline релиза**, но не среза корпусов: он фиксирует не «сколько чего
проиндексировано», а **что система говорит о себе** — что докладывает
`mb doctor`, выживают ли лаунчеры в затеняющем CWD, находится ли CLI,
спрятанный менеджером версий, какие пути в конфиге вообще перечисляются и
подхватывает ли живой демон изменение конфига. Ровно те вопросы, на которые
репортёру пришлось отвечать руками.

Машиночитаемый срез рядом: **`docs/v0.6.0-install-doctor-baseline.json`**.

---

## 1. Что чинилось

Восемь issues с одной чистой установки v0.5.1 на macOS. Общая форма у всех
одна: **инсталлятор вышел с кодом 0, все диагностики зелёные — а фича молча
не работает.**

| # | Симптом | Настоящая причина |
|---|---|---|
| 9 | `./install/install.sh` → `permission denied`, exit 126 | в индексе git режим `100644`, а не `100755` |
| 15 | после успешной установки `mb` → `command not found` | console-скрипты генерируются в `<engine>/.venv/bin`, который никто не кладёт в `PATH`; шимы в `bin/` тоже `100644` |
| 16 | `sh singularity/bin/mb` из `~/projects` → `ImportError … (unknown location)` | `-m` кладёт CWD первым в `sys.path`, каталог `singularity/` рядом становится namespace-пакетом и затеняет установленный |
| 10 | hooks Gemini молча пропущены при установленном `@google/gemini-cli@0.53.1` | наличие определялось по каталогу, версия — через `shutil.which`; nvm — функция шелла, невидимая неинтерактивному процессу |
| 11 | первый коммит в vault падает `Author identity unknown` | `D4-cli` проверял наличие бинарника `git`, а не способность коммитить |
| 12 | `mb index rebuild --code` бесконечно рапортует `files: 0` | демон обслуживает `Config`, захваченный при старте; `reload` перезагружал **индексы**, а не конфиг |
| 13 | `[PASS] K1-code-index: 0 chunk(s) from 0 file(s)` | «собрано, но из нуля файлов» проваливалось в ветку успеха |
| 14 | после переезда vault между ОС мёртвы 9 путей, доктор молчит про 8 из них | валидировался ровно один ключ (`code_repos_dir`) |

Отдельно стоит отметить #16: сам репорт был про `bin/`, но `-m` — это
механизм, и он был живым ещё в трёх местах, которые репорт не покрывал и все
из которых наследуют чужой рабочий каталог: спавн отсоединённого демона и
задачи планировщика во всех четырёх бэкендах. На Linux-раскладке из
собственного README (`git clone <url> ~/singularity` → `$HOME` содержит
`singularity/`) каждый ночной ребилд и каждый login-watcher умирали молча.

## 2. Воспроизведение

```bash
PYTHONIOENCODING=utf-8 python tools/install_doctor_baseline.py \
    > docs/v0.6.0-install-doctor-baseline.json
python -m pytest tests/ -q
```

`PYTHONIOENCODING` на Windows обязателен: голый редирект кодирует stdout в
кодовой странице консоли и корёжит в снимке всё не-ASCII. В PowerShell `>`
дополнительно дописывает UTF-8 BOM, который `json.load` не принимает —
снимать через `$out = & python …` и
`[IO.File]::WriteAllText(..., UTF8Encoding $false)`.

Скрипт отказывается снимать baseline, если `import singularity` разрешился не
в тот checkout, из которого он запущен — унаследовано от baseline v0.5.1 по
той же причине: снятый по чужому дереву baseline хуже, чем его отсутствие.

## 3. Что зафиксировано

### 3.1 Лаунчеры (#9, #15, #16) — `issue_9_16_launchers`

Каждый лаунчер прогоняется из **двух** каталогов, которые скрипт создаёт сам:
нейтрального и содержащего `singularity/`. Второй — это ровно родитель
стандартного клона.

| Лаунчер | нейтральный CWD | затеняющий CWD |
|---|---|---|
| `bin/_launch.py mb` | pass | **pass** |
| `bin/_launch.py imgqa` | pass | **pass** |
| `bin/_launch.py design-scout` | pass | **pass** |
| `sh bin/mb` | pass | **pass** |

Плюс режимы в индексе git — именно индекс, а не рабочая копия: на Windows
режим рабочей копии ничего не значит, а POSIX-клон получает именно индексный.

```
install/install.sh 100755 · bin/mb 100755 · bin/imgqa 100755 · bin/design-scout 100755
```

Признак возврата бага в снимке — поле `namespace_shadowed: true` в любой
строке (в stderr появилась сигнатура namespace-пакета `unknown location`).

### 3.2 Поиск CLI мимо PATH (#10) — `issue_10_cli_locator`

Раскладки менеджеров версий синтетические: реальный nvm нельзя предполагать
на произвольной машине, а проверяется здесь **порядок поиска**, а не эта
машина.

| Раскладка | Найден |
|---|---|
| `~/.nvm/versions/node/v24.19.0/bin` | да |
| `~/.nvm/versions/node/v18.20.0/bin` | да |
| `~/.volta/bin` | да |
| `~/.local/share/fnm/.../installation/bin` | да |
| три версии Node сразу | выбрана `v24.19.0` |

Последняя строка — не про «нашёл», а про **численный** порядок: лексикографи-
чески `v9` больше `v10`, и «самая свежая» стала бы самой старой.

### 3.3 Доктор (#11, #13, #14, #15) — `issue_11_13_14_15_doctor`

**`PASS 33 | WARN 2`**, обе WARN — настоящие находки, которых прежний доктор
не показывал никогда:

- `A6-config-paths`: три `gguf`-файла из `llm.models.*` физически отсутствуют
  на этой машине;
- `D7-cli-on-path`: `mb` резолвится в
  `…\Python310\Scripts\mb.exe`, а не в venv этого движка — то есть на vault
  отвечает **другая** установка Singularity.

Новые в этом релизе проверки: `A6-config-paths`, `D7-cli-on-path`,
`D8-git-identity`. В снимке они перечислены отдельным полем
`new_in_this_release`.

### 3.4 Пути в конфиге (#14) — `issue_14_config_paths`

Перечислено **10** путевых записей боевого конфига, включая
`llm.models.qwythos9b.args[14]` — ровно тот вложенный случай
(`--chat-template-file` внутри списка аргументов), который репорт называл
отдельно. В снимке только **ключи**: значения — дело этой машины.

Различаются два разных состояния: `foreign_os` (значение принадлежит другой
ОС — это не «пропало», это «с другой машины») и просто `missing`.

### 3.5 Живой демон и конфиг (#12) — `issue_12_live_config_reload`

Не мок: против **работающего** демона меняется безобидный ключ, затем всё
возвращается назад.

```
demon до записи                    excerpt_chars = 150
запись в конфиг                    excerpt_chars = 151
demon после записи, до reload      excerpt_chars = 150   <-- ровно баг #12
mb daemon reload                   config_changed: ["excerpt_chars"]
demon после reload                 excerpt_chars = 151
восстановлено                      excerpt_chars = 150
```

До фикса третья строка выглядела так же, а пятая — тоже `150`, и ничто об
этом не сообщало.

## 5. Чего этот baseline НЕ доказывает

- **Ни один из восьми багов не воспроизводился на исходной ОС.** Все репорты
  с macOS 15 / zsh; снимок сделан на Windows 11. Проверяется здесь поведение
  **после** фикса, причём часть механик на Windows принципиально другая:
  режим exec-бита не действует, `~/.local/bin` не используется (на Windows —
  ветка реестра), а `sudo`/nvm-раскладки просто отсутствуют. POSIX-половина
  `install/register_path.py` покрыта только тестами.
- **`A6-config-paths` не проверялся на настоящем кросс-ОС конфиге.** На этой
  машине Windows-пути — родные, поэтому ветка `foreign_os` в снимке пуста;
  она покрыта тестами на фикстуре из репорта, но не полевым прогоном.
- **`D7-cli-on-path` зафиксировал WARN, а не PASS.** На этой машине `mb`
  действительно принадлежит другой установке. Строка снимка описывает
  реальное состояние машины, а не эталон «как должно быть после установки».
- **Абсолютные значения нестабильны** по построению: `taken_at`, тайминги,
  число чанков, состав WARN зависят от машины. Эталонны `pass`-поля и метод
  снятия.
- **Гейт «install → PATH → mb работает» не прогонялся с нуля.** Полная чистая
  установка на свежей машине здесь не воспроизводилась; фаза 4e проверена
  юнит-тестами и своим `mb doctor`-чеком, а не сквозным прогоном инсталлятора.

## 6. Как ловить регрессию

- `namespace_shadowed: true` в `issue_9_16_launchers.runs` — вернулся `-m`
  где-то в цепочке запуска (или шим снова стартует пакет, а не файл).
- Любой режим ≠ `100755` в `executable_bit_in_index` — exec-бит потерян
  снова; это ловит и `tests/test_repo_file_modes.py`.
- `issue_12_live_config_reload.daemon_value_after_reload` ≠ записанному
  значению — `reload` опять перестал перечитывать конфиг.
- `K1-code-index` со статусом `PASS` и `0 file(s)` в тексте — вернулась #13,
  и вместе с ней исчезла проверка, которая ловит #12 первой.
