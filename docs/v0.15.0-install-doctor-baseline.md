## 1. What the release closed

The engine pushed text at three points — `SessionStart`, `PreToolUse`, `Stop` —
and none of them coincides with the moment "a task arrived". The first fires
before the task exists, the second after the action has been chosen. The
twelve-phase workflow therefore lived as a **skill**, that is, on pulling, and
across a full working day of real tasks it was never invoked once.

A rule is a constraint and can wait in context. **A chain is a procedure**: it
has to be entered, and entering happens once, in the first second of a task.
Prose in a prompt cannot enter anything.

Plus an audit of four code-authoring principles: two the system already carried,
one stood at exactly one point, and one was absent and conflicted with a rule
already in force.

## 2. What the baseline checks about this release specifically

The question for the snapshot here is **about delivery, not about the feature**.
Three consequences:

1. **A fourth Claude hook.** `UserPromptSubmit` is registered on a par with
   `SessionStart`, `Stop` and the two `PreToolUse` hooks. The doctor section must
   show `D9-route-hook` — before this release the router had no check at all, and
   a full PASS said nothing about whether it was installed.
2. **The phases became engine files.** The `v0110_package_layout` section carries
   the structural half: `singularity/workflow/` is a real engine directory,
   deployed together with the agents, rather than notes read out of
   `{{VAULT}}/workflow/` at the moment of use. The same boundary the preamble
   crossed in v0.13.0.
3. **The shape of SessionStart changed.** Two fragments were merged into one and
   two were added. The sections that resolve paths and read the config therefore
   matter more than usual: the machine must behave identically with no vault
   present.

## 4. One WARN, cleared before the snapshot — and it was a real one

The first snapshot gave **38 PASS and 1 WARN**: `B7-daemon — running but serving
code older than the files on disk`. The warning was genuine: the daemon had
started before this session rewrote the engine, and was serving the old modules.

That is exactly what the rule "a warm daemon serves the code it started with"
catches, and the check worked as intended. After `mb daemon restart` — PASS. The
snapshot was re-taken on a clean state; the original WARN is recorded here
because it characterises not the release but the daemon's life cycle on a
developer's machine, and passing over it would pass a re-take off as the first
result.

## 5. What this snapshot does not cover

- **Windows.** Three tests have failed there since v0.13.0 — two on rule delivery
  into agent files, one on a path separator in an assert (issue #17). Not a
  regression of this release and not touched by it. The run of macOS snapshots is
  six in a row, and the platform half has been unverified since v0.12.0.
- **The live shape of the `UserPromptSubmit` event.** The hook was checked against
  an event assembled from the documentation; there is no recorded fixture from a
  real client, unlike for Gemini and Grok. Noted as a known gap, not closed.
- **A parallel run.** `tests/test_plants.py` mutates real repository files for the
  duration of one subprocess. The suite is sequential; if xdist ever appears, that
  file will have to be isolated.
