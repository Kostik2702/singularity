## 1. What the release closed

`singularity/search/lexical.py` twice cited `tests/fixtures/search_eval.json` as
the grounds for not touching k1/b and RRF's k=60. **The file did not exist** —
neither in the repository nor in git history. For a year that sentence read as
evidence and was none: the same class as a green test that measured nothing, only
in a form the test suite cannot catch.

The set was built: 66 "query → note" pairs for memory, 16 for the code corpus,
quotas per class, and every pair's target chosen FIRST — so that the set could
report a bad number. The first honest reading of this vault: **R@1 0.485, R@5
0.712, MRR 0.585**.

The set settled two ranking questions (hybrid by default; the code corpus merges
unconditionally), **rejected a third** — a tie-break by how often a note is
opened cost 0.015 R@1 — and exposed four defects nobody was looking for.

## 2. How this snapshot differs from the previous one

**Section `v090_machine_config`, case 2, reversed the promise it checks — and
that is the snapshot's main change.**

Before v0.11.2 the case was called "the migrated file records decisions, not
defaults" and required that a value equal to `DEFAULT_CONFIG` **not** reach the
file. The file did stay short, but for the wrong reason, and the side effect had a
price: **a value could not be pinned**. While `hybrid_search` defaulted to
`false`, the command `mb config set hybrid_search false` deleted the key — that
is, no installation could opt out of a future change of default. The same thing
refuted the v0.6.3 promise about `vault_guard_enabled` for any sparse config.

The case is now called "the migrated file records every decision, default-valued
or not" and demands three things at once: a key the migrated file carried
survives a save; a key equal to the default does too; and the file is still
shorter than `DEFAULT_CONFIG` — because nobody pours defaults into `data`, and
what nobody set is simply absent there.

**Two new checks in block B:**

- `B6b-sessions` — the opt-in store of past sessions. Disabled is a `PASS`, not a
  warning: that it is a choice is the whole point. The size is stated out loud,
  because transcripts run to tens of megabytes and a silently growing store is
  discovered last.
- `B7-daemon` now tells "the daemon answers" apart from "the daemon answers with
  the code that is on disk". `reload` re-reads the config and the indexes and
  **never** re-reads modules. The first eval run produced a delta of exactly zero
  across all three classes to three decimal places — not because merging gives
  nothing, but because the branch had not been loaded. Recorded, that run would
  have left an eternal "hybrid does not help" under `docs/` — with numbers, and
  reproducible.

## 4. What this snapshot does NOT check

It does not measure search quality — there is a separate tool and separate
snapshots for that: `tools/search_eval.py`, `docs/search-eval-baseline.json`
(memory) and `docs/search-eval-code-baseline.json` (code). Their numbers depend on
a live vault and are comparable only within one session, which is why they do not
enter `all_pass`.

It does not check the session store in working mode: on this machine
`B6b-sessions` sees it disabled, and that is its normal state. An end-to-end check
was done by hand — 498 messages from 4 sessions, 0.6 MB, a search by identifier
found the right piece of the conversation, `mb sessions purge` deleted the store,
and the flag was returned to `false`.

It does not cover Gemini and Grok in session search: the parsing of their message
format is not written, and `mb sessions status` and `B6b-sessions` say so
themselves, not only this document.
