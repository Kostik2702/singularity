# v0.9.0 — baseline 2026-08-04 (the config leaves the vault)

Taken **2026-08-04** on master `ef3bb71` — the commit that already contains the
four fixes the first run found (§4); a snapshot on `1b27b9e` would have marked
them as defects rather than as verified code. Production vault, Windows 11
(10.0.26200), Python 3.10.6, vault `E:\obsidian\memory brain`.

The same tool (`tools/install_doctor_baseline.py`), the fourth snapshot in a row.
`all_pass: true`.

Machine-readable slice: **`docs/v0.9.0-install-doctor-baseline.json`**.

---

## 1. What the release closed

One defect, replicated across the codebase: **one person's machine, compiled into
the product as a default.**

| What it was | What it turned out to be |
|---|---|
| `DEFAULT_VAULT_WINDOWS = D:\obsidian\memory brain` | it outlived that very machine's move to another drive and travelled as a dead letter to everyone else |
| the config at `<vault>/.mb/config.json` | the vault travels between machines, and every absolute path inside it is wrong on arrival |
| `DEFAULT_ML_VENV = D:\venvs\imgqa-ml` | "the venv was not found at a path the user never chose" reads as a broken installation rather than an unconfigured one |
| `DEFAULT_INSTALL_DIR = E:/llama.cpp` | one machine's rule ("weights not on the system drive"), because of which a fresh `mb llm setup` downloaded gigabytes onto a drive that did not exist |
| a literal vault path in 18 skills and agents | the same thing, but in text the model reads |

The answer is the same everywhere: **there is no default — there is a decision,
and it is asked for once.** The installer asks for the vault path, `mb llm setup`
requires `--dir`, the ML venv is named through `IMGQA_ML_VENV` or a config key,
and the skills carry a `{{VAULT}}` token substituted at install time. The single
source of truth for the config is `~/.singularity.json`, created at installation.

The new `v090_machine_config` section checks exactly the promise the config moved
for:

1. **the upgrade is seamless** — a legacy config from the vault is adopted by the
   very first command, the values are preserved, and the old file remains as
   `config.json.migrated-<ts>`;
2. **decisions are written, not defaults** — a value equal to the standard one is
   not materialised into the file (otherwise the file would swell back to forty
   keys);
3. **an arriving vault does not overwrite a configured machine** — one's own
   config is always older than a foreign one;
4. **no shipped module names a drive letter** (except `C:\Windows`, which belongs
   to the OS rather than to the machine).

## 4. What had to be fixed for the snapshot to come out green

The first run gave `all_pass: false` in two sections — and both causes turned out
to be real rather than noise from the tool.

- **`MB_HOME` no longer isolates a run.** The `config_write_path` section planted
  a throwaway vault config; since v0.9.0 the command reads the machine file, which
  means the section was driving **this machine's real config** and failing on "no
  such section". Now `_mb` also substitutes `USERPROFILE`/`HOME` — `Path.home()`
  reads the first on Windows and the second everywhere else.
- **A daemon that started before the migration holds the OLD module.** Its
  `config_path` still resolves into the vault, so it keeps serving the file that
  was just renamed, and `mb daemon reload` answers "nothing changed". The settings
  look applied everywhere except where they are read. The product-side fix: the
  migration now says `run \`mb daemon restart\`` itself when it sees a live daemon
  (`config._daemon_running`).

Plus the drive-letter scanner found **four** places the release had missed:
`imgqa/external.py` (`D:\venvs\imgqa-ml`), `llm.py` (`E:/llama.cpp` and two
examples in hints), `reel/fonts.py` (`C:\Windows\Fonts` — legitimate, excluded),
and `register_gemini.py` (a comment). All were fixed in this same commit, that is,
the section was verified against the pre-fix tree.

## 5. What this baseline does NOT prove

- **It was taken on Windows** — mirroring v0.8.0, which was taken on macOS. The
  POSIX branches (symlinks in `~/.local/bin`, the scheduler branches) did not
  execute in this run; cross-OS coverage rests on the tests and on the v0.8.0
  snapshot.
- **The three WARNs at the time of the snapshot are honest.** `A6-config-paths`
  and `K1-code-index`: two entries (`code_repos_dir`,
  `projects.singularity.path`) pointed into `/Users/konstantingritsuk/projects` —
  that is the macOS machine the vault arrived from, and precisely the case the
  config became machine-local for. `D7-cli-on-path`: `mb` resolves to a different
  Singularity install (Python310\Scripts) rather than to this checkout's `.venv`.

  **Postscript (the same day, after the snapshot):** both entries were set for
  this machine through the CLI — `mb project add singularity "E:\Singularity"` and
  `mb config set code_repos_dir "E:\Project"`. That is not "the hardcoding came
  back": a path in the config is the machine's decision, a hardcoded path is one
  in the code that travels to everyone. On macOS those same keys will hold
  wherever the user cloned the repository. A second `mb doctor` gives **34 PASS /
  2 WARN**; what remains are the three missing `.gguf` files (the values cannot be
  guessed, and the cure is `mb llm add`/`mb llm remove`) and D7. The values in the
  JSON slice are the state at the time of the snapshot, not the "right" ones.
- **A clean install from scratch was not run** — as in every previous snapshot.
  The migration was verified on synthetic vault/home directories, and the
  `--vault` install by tests.
- **`reel` was merged as experimental** and has no check of its own in
  `mb doctor`; its surface is not covered by this snapshot at all.

## 6. How to catch a regression

- `v090_machine_config.cases[0].legacy_preserved_as` empty — the migration started
  deleting the original file instead of renaming it.
- `min_score_persisted: true` — `save()` materialises defaults again.
- The case "a configured machine is not overwritten" fails — an arriving vault
  overwrites the machine, exactly the class of loss the config moved to avoid.
- `offenders` non-empty — a default naming a drive is back in the code.
- `config_write_path` failing again with `exit_code: 1` — either the home
  isolation broke, or `mb config set` stopped resolving dotted notation (the
  v0.6.1 defect).
- `reload_reported_changed: null` with a live daemon — the daemon is reading the
  config from somewhere other than where the CLI writes it.
