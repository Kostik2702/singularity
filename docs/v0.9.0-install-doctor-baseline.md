## 1. Что закрывал релиз

Один дефект, растиражированный по кодовой базе: **машина одного человека,
вкомпилированная в продукт как дефолт.**

| Что было | Чем это оказалось |
|---|---|
| `DEFAULT_VAULT_WINDOWS = D:\obsidian\memory brain` | пережил переезд самой этой машины на другой диск и уехал мёртвой буквой ко всем остальным |
| конфиг в `<vault>/.mb/config.json` | vault ездит между машинами, и каждый абсолютный путь внутри него неверен по прибытии |
| `DEFAULT_ML_VENV = D:\venvs\imgqa-ml` | «venv не найден по пути, который пользователь никогда не выбирал» читается как сломанная установка, а не как ненастроенная |
| `DEFAULT_INSTALL_DIR = E:/llama.cpp` | правило одной машины («веса не на системном диске»), из-за которого свежий `mb llm setup` качал гигабайты на несуществующий диск |
| литеральный путь к vault в 18 скилах и агентах | то же самое, но в тексте, который читает модель |

Ответ везде один: **дефолта нет — есть решение, и его спрашивают один раз.**
Инсталлятор спрашивает путь к vault, `mb llm setup` требует `--dir`, ML-venv
называется через `IMGQA_ML_VENV` или ключ конфига, скилы несут токен
`{{VAULT}}`, который подставляется при установке. Единственный источник правды
по конфигу — `~/.singularity.json`, создаваемый при установке.

## 4. Что пришлось починить, чтобы снимок стал зелёным

Первый прогон дал `all_pass: false` в двух секциях — и обе причины оказались
настоящими, а не шумом инструмента.

- **`MB_HOME` больше не изолирует прогон.** Секция `config_write_path` подкладывала
  выброшенный vault-конфиг; с v0.9.0 команда читает машинный файл, то есть
  секция гоняла **реальный конфиг этой машины** и падала на «нет такой секции».
  Теперь `_mb` подменяет ещё и `USERPROFILE`/`HOME` — `Path.home()` читает первый
  на Windows и второй везде.
- **Демон, стартовавший до миграции, держит СТАРЫЙ модуль.** Его `config_path`
  по-прежнему резолвится в vault, поэтому он продолжает обслуживать только что
  переименованный файл, а `mb daemon reload` отвечает «ничего не изменилось».
  Настройки выглядят применёнными везде, кроме места, где их читают. Продуктовая
  часть починки: миграция теперь сама говорит `run \`mb daemon restart\``, если
  видит живой демон (`config._daemon_running`).

Плюс сканер букв диска нашёл **четыре** места, которые релиз пропустил:
`imgqa/external.py` (`D:\venvs\imgqa-ml`), `llm.py` (`E:/llama.cpp` и два примера
в подсказках), `reel/fonts.py` (`C:\Windows\Fonts` — легитимно, исключён),
`register_gemini.py` (комментарий). Все исправлены в этом же коммите, то есть
секция проверена на дофиксовом дереве.

## 5. Чего этот baseline НЕ доказывает

- **Снят на Windows** — зеркально к v0.8.0, снятому на macOS. POSIX-ветки
  (симлинки в `~/.local/bin`, ветки планировщика) в этом прогоне не исполнялись;
  кросс-ОС покрытие держится на тестах и на снимке v0.8.0.
- **Три WARN на момент снимка честные.** `A6-config-paths` и `K1-code-index`:
  две записи (`code_repos_dir`, `projects.singularity.path`) указывали в
  `/Users/konstantingritsuk/projects` — это macOS-машина, с которой приехал
  vault, и именно тот случай, ради которого конфиг стал машинным.
  `D7-cli-on-path`: `mb` резолвится в другой Singularity-инсталл
  (Python310\Scripts), а не в `.venv` этого чекаута.

  **Постскриптум (тот же день, после снимка):** обе записи заданы для этой
  машины через CLI — `mb project add singularity "E:\Singularity"` и
  `mb config set code_repos_dir "E:\Project"`. Это не «вернули хардкод»: путь в
  конфиге — решение машины, хардкод — путь в коде, который едет ко всем. На
  macOS в те же ключи ляжет то, куда пользователь склонировал репозиторий.
  Повторный `mb doctor` даёт **34 PASS / 2 WARN**; остаются три отсутствующих
  `.gguf` (значения не угадываются, лечится `mb llm add`/`mb llm remove`) и D7.
  Значения в JSON-срезе — состояние на момент снимка, не «правильные».
- **Чистая установка с нуля не прогонялась** — как и во всех предыдущих снимках.
  Миграция проверена на синтетических vault/home, установка `--vault` — тестами.
- **`reel` влит как experimental** и своего чека в `mb doctor` не имеет; его
  поверхность этим снимком не покрыта вообще.

## 6. Как ловить регрессию

- `v090_machine_config.cases[0].legacy_preserved_as` пусто — миграция начала
  удалять исходный файл вместо переименования.
- `min_score_persisted: true` — `save()` снова материализует дефолты.
- Кейс «a configured machine is not overwritten» упал — приехавший vault
  перетирает машину, ровно тот класс потери, ради которого конфиг переехал.
- `offenders` непустой — в код вернулся дефолт, называющий диск.
- `config_write_path` снова падает с `exit_code: 1` — либо изоляция home
  сломалась, либо `mb config set` перестал резолвить точечную нотацию (дефект
  v0.6.1).
- `reload_reported_changed: null` при живом демоне — демон читает конфиг не
  оттуда, откуда его пишет CLI.
